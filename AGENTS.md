# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, agy, codex, etc.) when working with code in this repository.

Ways of working are deliberately not repeated here. They live in the phpboyscout
skills, and naming a skill tends to age better than restating it, since the
restatement goes stale while the skill does not.

## What this is

`gitlab.com/phpboyscout/go/errorhandling` is a module in the [phpboyscout Go
toolkit](https://go.phpboyscout.uk). It is standalone: nothing else in the
toolkit depends on a shape it owns, and it carries its own documentation
microsite.

**It is not `go/errors`, and the two names invite exactly that confusion.**
[`go/errors`](https://errors.go.phpboyscout.uk) owns what an error *is* and what
it carries: `New`, `Wrap`, `NewSentinel`, `WithHint`, `WithAttrs`, `WithStack`,
the kind on every error, and `Is`/`As` through every layer. This module owns
what happens when one of those reaches the top of a run: the log level, the
process exit code, whether usage prints, whether the stack is rendered, and a
support message the error could not know about.

Nothing here wraps or re-exports a `go/errors` constructor; you import both. The
one fuzzy edge is that four sentinels live on this side (`ErrNotImplemented`,
`ErrRunSubCommand`, `ErrUnknownSubCommand`, `ErrAssertionFailure`). They are
error values in a reporting module because they are CLI concepts, and the point
of them is the disposition attached. Spec 0002 on the wiki makes that case.

## What it deliberately does not do

Nothing here calls `os.Exit`. `Fatal` reports and *returns* the code it believes
the process should use, and `main` decides. No signal handling, no panic
recovery, no redaction, no crash reporting, no output writer: reports go to the
`*slog.Logger` you were handed.

**A caller who wants a distinguishable exit code has to opt in twice, and
neither silence is an error.** Attaching an `Outcome` or a `WithExitCode` is the
first opt-in; the host reporting through this handler and acting on the code
`Fatal` returns is the second. In `go/signing-cli`, exactly one error carries an
outcome: the `keys` group's unknown-verb error, through
`errorhandling.UnknownSubCommand`, landing on `ExitCodeUsage` (2). Every other
failure there is plain, so its exit code is the host's business. go-tool-base
exits on what `Fatal` hands back; a host that drops the return value gets
nothing from any of this. `docs/reference/limitations.md` lists the rest,
including that an outcome quietly overrides the level and code the call site
asked for.

## Where it has got to

v0.5.0, pre-1.0, six tags since extraction from go-tool-base. Eight modules in
the group require it directly and none pick it up transitively, so every
consumer is a deliberate one: go-tool-base, `go/signing-cli`, keryx, krites,
phpbotscout, scoutdm, sigillum and skillup, all on v0.5.0 bar phpbotscout on
v0.3.0. The `ErrorHandler` interface, the exit-code helpers and the `HelpConfig`
seam are settled and safe to build on; `Outcome` is the newest surface, added to
replace a closed switch over three sentinels no consumer could extend. Releases
go through releaser-pleaser: a merged `feat` or `fix` updates a Release MR, and
merging that MR cuts the tag.

## The traps

**A new wrapper type here owes four methods, not one.** `Unwrap` is the obvious
part; the other three are not. Without `LogValue`, slog asks the outermost value
only and gives up rather than unwrapping, so a wrapper of ours on the outside
flattens the record to a bare string, losing the kind, the hint, the details and
every attribute. Without `StructuralKind() bool` returning true, this module's
plumbing becomes the `kind` a log query filters on instead of what the error is.
`ErrorPayload` is what gets the code onto a record. Both omissions shipped and
were fixed, in v0.4.0 and v0.5.0, so copy `exitcode.go` or `outcome.go`.

**Reaching for another module fails a test that does not look like a dependency
check.** `depfootprint_test.go` runs `go list -deps` and rejects Cobra, pflag,
viper, charmbracelet, OpenTelemetry and the cloud SDKs by prefix, so the toolkit
reflex inverts here. The only dependency outside tests is `go/errors`, which is
stdlib-only, and the design leans on that: `SetUsage(func() error)` and
`HelpConfig` exist to keep a CLI framework and a support channel on the caller's
side.

**The published mocks are regenerated by hand.** `mocks/` is public surface that
consumers import, and nothing runs mockery: not `just ci`, not the CI
components. The guard is a pair of compile-time assertions in `mocks_test.go`,
added after a stale `MockErrorHandler` shipped through v0.3.0 and broke
consumers' tests rather than this repo's.

## The quality gate

`just ci` runs the repo's own checks (`tidy`, `test`, `test-race`, `lint`). Run
it before raising a merge request, so CI confirms rather than discovers.

## Which skills apply here

| When | Skill |
|---|---|
| Deciding whether something belongs here or in `go/errors` | `deep-modules` |
| A change here needs something `go/errors` does not offer yet | `raise-a-forge-issue` |
| Reaching for a dependency for config, HTTP, CLI, logging, forge or credentials, where the answer here is almost always no | `use-the-go-toolkit` |
| Checking this module against the estate's shape | `create-a-go-module` |
| Changing behaviour a spec decided; specs 0001 to 0003 are on this project's wiki and the source cites them by number | `spec-driven-development` |
| Writing anything that states what a sentinel, an exit code or a log field does | `checkable-claims` |
| Writing or restructuring this module's documentation, which is its own microsite | `diataxis-docs` |
| Before `glab mr create` on this repo | `verify-before-pr` |
| Writing a commit message or a merge request description | `conventional-commits`, `pre-1-0-release-safety` |
| Committing, branching, merging, or opening a merge request | `forge-publish-workflow` |

Two seeded skills look like they apply and do not. `env-gated-integration-tests`
has nothing to gate, since this module touches nothing external. And
`race-safe-test-injection` has nothing to fake: every test runs `t.Parallel()`
against a handler built as a struct literal with its own capture logger.

## House rules

- Linear history. Rebase and fast-forward; never squash-merge from the UI.
- Conventional Commits, and the type decides whether a release is cut. Only
  `feat` and `fix` release. A change that repoints or removes a public interface
  is `feat`, not `refactor`, or it lands and never ships.
- No AI attribution in anything published, and never at-mention anyone.
- Never cut a release yourself. That is the maintainer's call, every time.
